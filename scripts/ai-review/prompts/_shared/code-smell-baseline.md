## Code Smell 基準清單

**⚠️ 重要原則**：這份清單是「啟發式建議，非硬性違規」。專案自身的既有慣例優先於此基準——若專案慣例明確允許某種寫法，即使在此清單中被視為 code smell，亦不應回報。

1. **Improper Naming (命名不當)**
   - 定義：變數、函式或類別的名稱無法清楚表達其用途或行為。
   - 修法：重新命名以準確反映其職責。

2. **Duplicated Code (重複邏輯)**
   - 定義：相同或極其相似的程式碼片段出現在多個地方。
   - 修法：將重複邏輯提取為共用函式或元件。

3. **Feature Envy (特性羨慕)**
   - 定義：一個模組頻繁地存取另一個模組的資料或方法，而非專注於自身的職責。
   - 修法：將該方法或邏輯移動到被頻繁存取的資料所屬的模組。

4. **Data Clumps (資料群聚)**
   - 定義：一群變數總是結伴出現並一起傳遞（例如多個相同的參數）。
   - 修法：將這些變數封裝成一個物件或資料結構。

5. **Primitive Obsession (原始型別執著)**
   - 定義：過度使用基本資料型別（字串、數字）來表示具有特定領域意義的概念。
   - 修法：為該概念建立專用的型別或物件來進行封裝。

6. **Repeated Switches (重複條件判斷)**
   - 定義：同樣的 `switch` 或 `if/else` 條件判斷出現在程式碼的許多不同地方。
   - 修法：運用多型（Polymorphism）或策略模式來取代重複的條件分支。

7. **Shotgun Surgery (散彈式手術)**
   - 定義：每次新增或修改一個功能時，必須同時修改多個不同的檔案。
   - 修法：將相關行為集中並移動到同一個模組內。

8. **Divergent Change (發散式變更)**
   - 定義：同一個模組因為多種不同的原因而經常被修改。
   - 修法：根據單一職責原則，將該模組拆分為多個職責單一的模組。

9. **Speculative Generality (投機性泛化)**
   - 定義：為了預期未來「可能」會用到的功能，而寫了過多現在根本用不到的泛化與抽象邏輯。
   - 修法：移除不必要的抽象，保持程式碼的精簡（YAGNI原則）。

10. **Message Chains (訊息鏈)**
    - 定義：連續呼叫多個物件的方法來獲取資料（例如 `a.getB().getC().getD()`）。
    - 修法：隱藏委託細節，讓物件直接提供需要的方法。

11. **Middle Man (中間人)**
    - 定義：一個模組大部分的方法都只是單純委託給另一個模組，沒有提供實質邏輯。
    - 修法：移除中間人，讓呼叫者直接與真正做事的模組互動。

12. **Refused Bequest (拒絕繼承)**
    - 定義：子類別繼承了父類別的方法或屬性，但完全用不到或試圖隱藏它們。
    - 修法：重新檢視繼承關係，考慮使用組合（Composition）來取代不適當的繼承。
