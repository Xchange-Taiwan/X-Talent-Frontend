# ADR 0002: Auth & Session Strategy

- **Status:** Reconciled via retro interview (2026-08-04). Several items remain genuinely unresolved (recorded below as-is, not guessed at) — the user declined to file follow-up tracker tickets for them, so they exist only in this document until someone picks them up.
- **Date range covered:** 2024-01-15 (initial NextAuth setup) → 2026-08-04
- **Scope:** All authentication and session-management architecture in X-Talent-Frontend, plus the X-Talent-Backend/BFF touchpoints it depends on. Supersedes/absorbs [ADR 0001](./0001-session-hint-header-sync.md) as the high-level record for this domain — 0001 remains as the detailed PR-by-PR account of the session-hint mechanism specifically.

## Why this ADR exists

None of the decisions below were recorded anywhere at the time they were made — no ADRs, and mostly no tracker tickets either. Several were direct commits to `develop` with no PR. This document reconstructs the architecture's actual evolution from git history, PR bodies, and tracker issues, then a retro interview fills the gaps that only exist in someone's memory.

## Current-state architecture (as of 2026-08-04)

- **Session strategy:** NextAuth v4, JWT strategy (`src/auth.config.ts:46`) — no database-backed sessions on the frontend.
- **Providers:** Both registered as NextAuth `CredentialsProvider`, not a standard OAuth provider:
  - `credentials` — email/password, posts to BFF `POST /v1/auth/login` (`auth.config.ts:49-105`).
  - `custom-google-token` — Google's OAuth code exchange happens _outside_ NextAuth via a server action (`src/lib/actions/googleCallback.ts`), then the result is fed into NextAuth via `signIn('custom-google-token', ...)` (`src/lib/auth/oauthOutcome.ts:43-103`, `auth.config.ts:107-160`). This is a hand-rolled bridge, not NextAuth's built-in Google provider.
- **Token refresh:** BFF rotates the refresh token on every `/v1/auth/token` call and revokes the old one immediately. Concurrent refreshes are coalesced through a single-flight map (`auth.config.ts:32-43`). Google's refresh token is bridged server-side via a short-lived (60s), client-JS-invisible cookie (`src/lib/auth/oauthRefreshBridge.ts`).
- **Middleware** (`src/middleware.ts`): verifies JWT signature+expiry via `getToken` (not just cookie presence), handles maintenance mode, redirects unauthenticated users off protected routes, and syncs the session-hint cookie (see ADR 0001 for that mechanism's own history).
- **Backend session state:** DynamoDB-backed BFF refresh-session records exist (`X-Talent-Backend/src/xtalent/contexts/bff/adapters/outbound/session/dynamodb.py`), but per the backend's own in-repo OpenSpec proposal (`docs/openspec/changes/migrate-auth-session-token-lifecycle/proposal.md`), the migration to this model is **not fully complete** — logout and OAuth-style refresh routes reportedly still lack a migrated implementation as of that document.
- **Service-to-service auth (`x-api-key`):** only confirmed present in a sensitive-header redaction list in the backend; issuance/verification logic was not found in application code — may live at an infra layer (`X-Talent-infra`, not yet investigated).

## Divergences from root CLAUDE.md

- **"Google OAuth + email/password credentials"** is technically true but misleading — there is no NextAuth Google _provider_ in use. Google auth is a hand-rolled code-exchange-then-bridge-into-credentials-provider flow, not a standard NextAuth OAuth integration.
- **"Session state: DynamoDB (via BFF)"** — real, but the backend's own migration proposal suggests it's not fully rolled out to all auth routes yet. Treat as in-progress, not settled.
- **"Service-to-service auth: shared x-api-key header"** — only weakly confirmed; not found in application-level issuance/verification code within this research pass.
- Repo-layout section is separately known stale (see memory: monorepo layout drift).

## Resolved via retro interview (2026-08-04)

1. **LinkedIn auth (2024-12, added then removed within ~1 month):** Confirmed a deliberate product decision to remove it, not a technical dead end. The specific reasoning is no longer recalled.
2. **`352fd63` "downgrade NextAuth to fix Google OAuth" (2025-11-22):** Confirmed this was a real downgrade from `next-auth@5.0.0-beta.4` back to `4.24.13` (currently pinned at `4.24.15` — still v4, never revisited). Root cause: upgrading to v5 beta caused the Google OAuth flow to enter a page-refresh loop. **Whether this is still a live constraint against upgrading to v5 (now stable) is unverified** — nobody has confirmed one way or the other. **Anyone considering a NextAuth v5 upgrade must re-test the Google OAuth flow for a refresh loop before assuming it's safe** — do not treat the current v4 pin as arbitrary.
3. **Refresh-token client exposure (`b7a5256`, 2026-04-26) → reversal (`6f13ef1`, 2026-05-06):** Confirmed this was **not** a considered production security tradeoff — the token was exposed for local debugging convenience, pre-launch, before the app had real users. No user data was ever actually at risk during the exposure window; it was corrected once flagged by the AI security review. Classify as a process gap (temporary debug code not reverted before merge), not a security incident.
4. **BFF signing-key impersonation vuln (Tracker #299, fixed 2026-07-26):** **Unresolved.** Whether any forensic check was done for prior exploitation, and whether invalidating all existing tokens on deploy caused user-facing fallout, could not be recalled. The user declined to file a follow-up tracker ticket for this — it is recorded here as an open security-relevant gap for whoever revisits this area next.
5. **Session-hint mechanism origin (`6ca6d37`, 2026-07-23, direct-to-develop, no PR/ticket):** **Unresolved.** Could not recall whether skipping review was deliberate (e.g. treated as a trivial/urgent change) or simply happened. No follow-up ticket filed.
6. **Backend DynamoDB session-migration OpenSpec proposal status:** **Unknown to the frontend side** — needs a direct check with the backend team. Not filed as a ticket; flagged here only.
7. **`x-api-key` service-to-service auth — real and enforced somewhere, or not:** **Unknown to the frontend side** — possibly enforced at an `X-Talent-infra` / API Gateway layer not covered by this research. Not filed as a ticket; flagged here only.

**Meta-observation:** 3 of these 7 items resolved to "no longer recalled" or "unknown" rather than a concrete answer — all undocumented decisions more than a few months old. This is the strongest argument for writing ADRs going forward rather than relying on memory: the reconstruction window closes fast.
